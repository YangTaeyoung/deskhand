# RDP 성능 실측 — 2026-10-22

현재 기본 정책(창 1포인트당 원격 1픽셀)의 실제 Windows 11 ↔ Mac 연결을 측정했다. 브랜치는 `feat/phase2-integration`, HEAD `b907c1d`와 미커밋 RDP 구현이며 원격 저장소는 없다.

## 현재 확인된 값

| 조건 | 원격 해상도 | Windows 출력 FPS 중앙값 / 범위 | 인코딩 시간 중앙값 | Mac 앱 CPU | Mac 앱 RSS 중앙값 |
|---|---|---|---|---|---|
| 작은 창 | 1020×601 | 31 / 30–35 | 3ms | 21.7% | 175.8MiB |
| 큰 창 | 2748×1463 | 31 / 22–34 | 19ms | 119.1% | 506.1MiB |

CPU는 코어 하나의 전체 사용량을 100%로 계산했다. 119.1%는 약 1.19코어이며 Mac 전체 CPU 사용률 119%라는 뜻이 아니다. RSS는 `ps` 프로세스 상주 메모리이며 WindowServer/GPU 메모리 전체를 포함한 값이 아니다.

두 조건 모두 Windows 자원 부족에 따른 서버·네트워크·클라이언트 프레임 누락 카운터는 0이었다. Windows Frame Quality 카운터는 작은 창 100, 큰 창 45였다. 이 수치를 사람의 주관적 화질 점수로 해석하지 않는다. 큰 창의 평균 출력은 29.1fps이며 순간 22fps까지 내려갔다. 중앙값만으로 일정한 프레임 간격을 통과시킬 수 없다.

**여기서 FPS는 Windows가 클라이언트에 제공한 출력 수다. Mac 앱의 수신·화면 제출·모니터 표시 완료 FPS와 구분한다.** [Microsoft 카운터 정의](https://learn.microsoft.com/en-us/azure/virtual-desktop/remotefx-graphics-performance-counters).

## 시험 방법

- 동일한 자체 WinForms 시험을 각 조건에서 40초 실행했다. 원격 화면 전체의 배경색을 계속 바꾸고 도형 18개를 이동시켰다. 시험 창은 자동 종료했고 기존 사용자 앱을 종료하거나 Windows를 로그오프하지 않았다.
- 폼 Paint 타임스탬프에서 안정 구간 5–35초의 생성 빈도는 각각 39.90 / 39.81회/초였다. 60fps 영상 생성 시험이 아니다.
- `Win32_PerfFormattedData_Counters_RemoteFXGraphics`의 실제 `RDP-Tcp 0` 인스턴스를 1초 간격으로 28번 조회했다. 시작·종료 경계 각각 2개를 제외한 24개 샘플을 표에 사용했다. 원시 28개는 보존했다.
- Mac `ps` CPU 누적 시간의 차이를 실제 경과 시간으로 나눴다. 초기 구간을 제외하고 시작 후 7–34초의 샘플을 사용했다.
- 작은 창과 큰 창 사이에는 RDP를 재접속하지 않았다. 모니터 전원 켜기·드라이버 설치·Windows 설정 완화는 없었다.

원시 자료와 실행·집계 스크립트: `build/validation/20261022-rdp-perf/`의 `logical-{small,large}-{summary,counters,mac-process,motion}.json`, `motion.ps1`, `counters.ps1`, `run.py`, `summarize.py`.

## 앱 내부 계측과 남은 확인

서버 FPS만으로 실제 Mac 앱을 통과시키지 않기 위해 `RDPPerformance.swift`에 1초 단위 네이티브 갱신·Swift 수신·레이어 제출 횟수, 제출 간격 p50/p95/최대값·100ms 초과 간격을 추가했다. 데이터는 크기·횟수·시간뿐이며 화면 픽셀·사용자·암호·호스트 정보를 기록하지 않는다. 고유 sequence를 제출한 경우만 집계하고, 해상도 전환 시 구간을 분리하며, 시간 간격 배열은 256개로 제한했다. 같은 sequence를 레이어에 중복 지정하지 않도록 수정했다.

이 계측의 '제출'은 CALayer contents 지정이며 실제 모니터 표시 완료 fence가 아니다. 프레임 병합·중복·정지·해상도 전환 검증 3개와 viewport/native 관련 테스트 9개가 통과했고 앱 빌드·서명도 통과했다. 계측 빌드로 앱을 재실행했고 현재 사용자 로그인 대기 중이다. 로그인 후 두 창 크기에서 앱 내부 계측을 추가 수집해야 한다.

수정 전 약 5K 해상도와 동일한 조건의 FPS 실측은 남아 있지 않으므로 '픽셀 75% 감소 = FPS 4배'로 환산하지 않는다. 현재 결과는 약 30fps 출력과 큰 창의 높은 비용을 확인한 것이며 60fps·전체 상업용 품질 통과 판정이 아니다.
