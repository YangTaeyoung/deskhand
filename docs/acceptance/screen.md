## 2. 방법

  - `motion1920`: 같은 fixture, `max_width` 1920, 30초.
  - `input`: fixture(정지)에 클릭 20회, Space 20회(§4).
  - `click`·`click1000`(M7): fixture(정지)의 첫 번째 Same 버튼을 사람처럼 포인터를 움직인 뒤 클릭한다(§9.2).
  - `keyframe`(M6): fixture(정지)를 띄우고, 새 `video` 스트림의 첫 AU 10회, 한 스트림에서 `keyframe` 요청 10회, 같은 설정의 `config`(인코더 재생성) 10회, `max_width` 1920과 원본을 오가는 `config`(출력 해상도 변경) 10회의 키프레임을 받고, 받은 직후마다 `screen.capture`(PNG, `max_width` 1920)를 찍는다(§8.1).
  - 모두 `video` 헤더 기본값(60 fps, 원본 4K는 20 Mbps, 1920은 6 Mbps).
- 시계 보정: 연결마다 측정 앞뒤로 `time.sync` 50회(5 ms 간격). 오프셋(에이전트 `mono_us` − 프로브 시계)은 RTT가 가장 작은 왕복의 `mono_us − (보낸 시각 + 받은 시각)/2`. 프로브 시계는 QPC.
- 캡처→수신 = 프로브 수신 시각 − (`capture_mono_us` − 오프셋). 첫 AU(인코더 생성 직후)는 따로 적고 분포에서 뺐다. 캡처→인코딩 완료는 `encode_done_mono_us − capture_mono_us`(에이전트 시계만 씀).
- 10초 반복 AU(protocol §4: 10초 동안 AU가 없어 마지막 이미지를 다시 인코딩한 AU)의 `capture_mono_us`는 이미지를 얻은 시각이 아니라 그 인코딩을 시작한 시각이다. M6부터 프로브는 앞 AU 캡처로부터 10.00–10.05초 뒤에 찍힌 키프레임 아닌 AU를 반복 AU로 보고 지연 분포에서 뺀다(n에 넣지 않는다). §3의 M5 `static` 행은 반복 AU 5개를 넣은 값이고, 같은 기록을 이 규칙으로 다시 계산하면 캡처→수신 10.24 / 100.12 ms(n 9), 캡처→인코딩 완료 9.94 / 92.43 ms다.
- 비트레이트·fps 평균은 스트림을 연 때부터 닫을 때까지의 AU 바이트·개수. 에이전트 `stats`(1초마다)도 함께 적었다.
- 디코딩: `ffmpeg -v error -i <x>.h264 -f null -`의 오류 줄 수, `ffprobe -count_frames`의 프레임 수.
- 백분위는 최근접 순위.
- GPU 상태(M7): 프로브가 PC에서 `nvidia-smi --query-gpu=pstate,clocks.gr,clocks.video --format=csv,noheader,nounits -lms 50`(읽기 전용 질의)을 자식 프로세스로 돌려 줄마다 프로브 시계로 찍고, 측정이 끝나면 그 프로세스를 끝낸다. 입력의 GPU 상태는 그 입력을 보내기 직전(200 ms 안)의 표본이다. 드라이버가 보고하는 클록 값은 약 200 ms마다 바뀐다.

### 2.1 시계 보정의 불확실성

| 실행 | 최소 RTT | RTT 중앙값 | 빠른 8회 오프셋 폭 | 측정 뒤 오프셋 변화 |
|---|---|---|---|---|
| static | 0.168 ms | 0.198 ms | 0.021 ms | +0.001 ms |
| motion | 0.170 ms | 0.229 ms | 0.023 ms | −0.001 ms |
| motion1920 | 0.172 ms | 0.206 ms | 0.070 ms | −0.001 ms |
| input | 0.169 ms | 0.214 ms | 0.021 ms | −0.002 ms |

- 왕복 오차 한계는 최소 RTT의 절반, 약 ±0.09 ms.
- 에이전트의 `mono_us`는 Go 단조 시계이고, Windows에서 Go 1.26.0의 단조 시계는 `KUSER_SHARED_DATA`의 인터럽트 시각을 읽는다(`runtime/sys_windows_amd64.s:200`, `nanotime1`). 이 값은 타이머 틱마다(측정 중 1 ms) 바뀌므로, 같은 PC에서 Go 단조 시계의 증가 폭은 p50 1 ms(최소 0.44, 최대 1.69 ms, 1초 표본)였다. 그래서 에이전트가 찍는 `capture_mono_us`·`done_mono_us`는 실제보다 0–1 ms 이를 수 있고, 이 값을 쓰는 지연(캡처→수신, 주입 완료→변화 캡처)은 0–1 ms 크게 나올 수 있다. `time.sync`는 프로브가 5 ms 잠든 뒤(틱 직후) 보내므로 그 오차가 작고 빠른 8회의 오프셋 폭이 0.02–0.07 ms로 모였다.
- 결론(오차 = 측정값 − 참값):
  - 에이전트 시각이 끝점인 값(송신→주입 완료): −1.1 ~ +0.1 ms. 에이전트 시각이 이르면 값이 작게 나온다.
  - 에이전트 시각이 시작점인 값(캡처→수신, 인코딩 완료→수신): −0.1 ~ +1.1 ms.
  - 에이전트 시각끼리의 차(캡처→인코딩 완료, 주입 완료→변화 캡처): 두 시각이 각각 0–1 ms 이를 수 있어 −1 ~ +1 ms.
  - 프로브 시계만 쓴 값(ACK 왕복, 송신→변화 AU 수신)은 QPC라 이 오차가 없다.
  - 1 ms 틱보다 작은 차이(예: 클릭 up의 송신→주입 완료 0.29 ms와 Space up의 0.28 ms)는 잡음과 구별되지 않는다.
- DD 경로의 `capture_mono_us`는 직접 읽은 단조 시계가 아니라 `qpcMono(LastPresentTime)`(`internal/agent/capture/open_windows.go:313`, 호출은 `dd_windows.go:289`)이다. 변환하는 순간 QPC를 읽고 이어서 Go 단조 시계를 읽은 뒤, 단조 시계 값에서 (그 QPC − `LastPresentTime`)을 µs로 바꿔 뺀다. 뺄셈은 QPC끼리라 틱 오차가 없으므로 오차는 변환 순간에 읽은 단조 시계 값 하나에서만 오고, 위와 같은 영역(실제보다 0–1틱 이름)이다. 틱은 present 순간이 아니라 변환 순간의 것이다. 두 읽기 사이 몇 µs만큼 반대쪽(늦게)으로 치우치지만 틱보다 훨씬 작다. present가 1초보다 오래됐거나 QPC가 그 present보다 앞서면 변환 순간의 단조 시계 값을 그대로 쓴다. GDI 경로의 프레임과 같은 이미지를 다시 인코딩한 AU(10초 반복, M7 예열)의 `capture_mono_us`는 단조 시계를 직접 읽는다. 그래서 위 결론은 `capture_mono_us`의 세 출처 모두에 그대로 맞다.
- 틱은 `NtQueryTimerResolution`이 보고하는 PC 전체의 현재 타이머 해상도로, 이 PC는 모든 실행의 앞뒤에서 1.0 ms였다(그 해상도를 요청한 프로그램이 따로 있다). 그 값이 기본값(15.6 ms)인 PC에서 이 오차가 그만큼 커지는지는 확인 필요.

## 5. 발견

### 5.1 원본 해상도 첫 IDR이 검은 화면

8개 스트림 중 7개(4K 6개 전부, 1920 2개 중 1개)의 첫 AU(IDR)가 전부 검은 화면이다(4K 2,249 B, 1920 657 B; 디코딩한 첫 프레임의 밝기 최댓값 0). 다음 AU(P 프레임, 39–74 KB)가 4.9–76 ms 뒤 캡처한 화면 내용을 담고, 받는 쪽에서는 첫 AU 수신 뒤 5–18 ms 안에 도착했다. M6에서 원인을 확인하고 고쳤다(§8.1).

### 5.2 드문 프레임의 인코딩 지연

연속 움직임에서 캡처→인코딩 완료는 14.65 ms(4K)인데, 프레임이 드물 때(static, input)는 24–30 ms(p50)이다. 입력→화면 지연에서 가장 큰 몫이다. M6에서 원인(GPU가 쉬는 동안의 낮은 클록)을 확인했다(§8.2).

### 5.3 버튼 down 주입 시간

클릭 down의 ACK가 13.6 ms(p50)로 up(0.6 ms)이나 Space down(2.5 ms)보다 길다. 에이전트는 down과 up을 같은 경로로 처리하고 차이는 `SendInput` 호출 안에서 생긴다(송신→주입 완료 13.1 ms 대 0.3 ms). M6에서 잰 결과 그 시간은 저수준 훅 앞, Windows 입력 처리 안에서 다음 화면 합성까지 기다리는 시간이다(§8.3).

### 6.1 측정하지 않은 것

- **Mac↔PC 네트워크 구간.** PC 방화벽은 모든 프로필에서 켜져 있고 기본 인바운드 동작은 `NotConfigured`(Windows 기본값 차단)이며, Deskhand 허용 규칙은 설치된 에이전트의 UDP 47600뿐이다(다른 포트로 실제로 닿는지는 시험하지 않았다). 테스트 에이전트를 다른 포트로 띄우라는 결정과 보안 설정을 바꾸지 말라는 결정을 함께 지키려고, 방화벽 규칙을 더하지 않고 프로브를 PC에서 루프백으로 돌렸다. 그래서 위 지연에는 네트워크가 빠져 있다(인코딩 완료→수신 0.5–1 ms는 루프백 QUIC과 에이전트 쓰기 큐). 참고로 Mac→PC TCP 연결 왕복(포트 22, 40회)은 p50 4.68 / p95 15.10 ms(최대 69.3 ms)였다. 재측정: P1 병합 때 설치된 에이전트(47600)에 Mac의 `screen-probe run -addr <PC>:47600`으로 붙거나, 사람이 임시 방화벽 규칙을 허락하면 `run.sh`의 프로브를 Mac에서 돌린다.
- RDP 표시 상태(위 표).
- CPU 사용률(M3에서 4K60 움직임 논리 CPU 1개의 약 20.9%로 측정).

### 8.3 버튼 down의 `SendInput` 시간 — 원인은 Windows 입력 처리, 고치지 않음

- 에이전트 코드가 아니다: 에이전트는 `SendInput`을 한 번 부르고, 그 호출 자체가 13–16 ms 걸린다(진단 테스트에서 down p50 15.33 ms, 최소 11.10, 최대 16.44; up 0.37; 같은 점으로 이동 0.18).
- 다른 프로그램의 저수준 훅이 아니다: 테스트가 `WH_MOUSE_LL` 훅을 마지막으로(사슬의 맨 앞에) 걸었을 때 그 훅이 `SendInput` 시작 15.43 ms(p50) 뒤에야 불렸고, 그 안의 `CallNextHookEx`(나머지 훅 전부)는 0.004 ms(최대 0.152)였다. 훅이 이벤트를 삼키면(창에 닿지 않음) `SendInput`이 0.27 ms였다(삼키기 시작한 첫 번만 13.57 ms). 주입한 프로세스에는 시스템 밖 DLL이 없었고 `win32u!NtUserSendInput`의 앞부분은 손대지 않은 시스템 호출 코드(`4c 8b d1 b8 7a 10 00 00`)였다.
- 다음 화면 합성까지 기다린다: `DwmFlush` 직후 x ms에 down을 넣으면 `SendInput`이 16.7 − x ms 걸렸다(x = 0, 2, …, 14에서 16.72, 14.85, 12.97, 11.10, 8.99, 7.10, 5.08, 3.09 ms; x = 16에서는 다음 합성까지 17.62 ms).
- 대상에 따라 다르다: fixture의 `Same` 버튼(BUTTON) 위 down은 매번(쉬는 시간 0.2초·0.6초·3초, 이동과 한 묶음, 절대 좌표를 실은 down 모두 14.65–16.82 ms), Edit 위는 처음 두 번(15.06, 15.78 다음 0.50, 0.39), fixture 창 자체의 빈 곳은 창을 앞으로 가져온 뒤나 버튼을 누른 뒤 처음 한 번(8.71–16.97)만 기다렸고 그 뒤는 대부분 0.33–0.53 ms였다(처음 것을 뺀 50여 회 중 2회가 10.47, 13.04 ms). 빈 곳 down 앞에 3픽셀 이동이나 키 입력(그 창이 다시 그림)을 넣어도 대부분 0.35–0.48 ms였다.
- 결론: 기다림은 저수준 훅이 불리기 전, Windows 입력 처리 안에서 다음 DWM 합성까지다. Deskhand가 없앨 수 있는 시간이 아니고, 다른 프로그램이 원인이라는 증거도 없다. 그대로 두었다. 이 PC의 세션에는 입력을 지켜볼 수 있는 프로그램(Discord, Razer Central·Cortex, KakaoTalk, 1Password, `StSess.exe`·`nosstarter.npe`·`delfino.exe`·`I3GProc.exe`·`CrossEXService.exe` 등)이 떠 있으나 건드리지 않았다. Windows 안의 정확한 경로(커널 ETW 스택이 필요)와 다른 PC에서도 같은지는 확인 필요.

## 9. M7: 입력 중 인코더 예열

측정: 2026-10-20(KST), 같은 PC·같은 방법(별도 테스트 에이전트, 콘솔, 루프백). 최종 실행은 22:41–22:46, 에이전트 `4dbe894`. 비교 기준은 22:37–22:41에 같은 프로브로 잰 M6 에이전트(`171a9ce`)다. Windows 테스트는 `scripts/wintest.sh`로 돌렸다.

### 9.1 규칙과 그 근거

규칙은 protocol §4다. 에이전트가 입력을 주입한 뒤 750 ms 동안 화면이 그대로면, 1/min(60, `max_fps`)초마다 마지막 이미지를 다시 인코딩해 보낸다. 다만 다음 경우에는 다시 인코딩하지 않는다:
- 인코더에 프레임이 남아 있을 때
- 포인터 이동이 아닌 입력 뒤 50 ms 동안
- 새 이미지를 얻은 뒤 그 간격의 1.25배 동안

구현:
- `input.Injector.LastInjected`가 마지막 주입 시각과, 포인터 이동이 아닌 마지막 입력의 시각을 준다.
- 파이프라인은 그 둘로 순수 함수 `warmDue`(`internal/agent/screen/warm.go`)가 판정한다.
- 창 동안에는 DD 소스를 기다리지 않고 1 ms마다 본다.

두 예외를 둔 근거. 22:13–22:15에 750 ms·60 fps 규칙만 적용해 먼저 쟀다:
- `click`(첫 이동 340 ms 뒤 클릭)의 클릭 down이 63.5 / 79.8 ms로, 예열이 없는 M6 에이전트(59.9 / 62.9 ms)보다 나빴다.
  - 클릭 때 GPU는 20번 중 14번 P8이었다.
  - 그 클록에서 예열 프레임 한 장의 인코딩은 약 28 ms다.
  - 바뀐 화면은 그 뒤에 줄을 섰다(캡처→인코딩 완료 최대 56 ms).
- `input`은 52.5 / 60.0 ms였다. 바뀐 프레임의 캡처→수신이 약 21.5 ms였고, 그중 약 7.6 ms는 앞선 예열 프레임(13.5 ms)을 기다린 몫이다.
- 입력 뒤 50 ms 예외를 넣은 뒤(22:23–22:27)에는 `click` 52.2 / 55.9 ms, `input` 47.1 / 59.5 ms였다. 최종 값은 §9.2에 있다.
- 새 이미지 뒤 예외: 이 예외가 없으면 다음 예열 시각(앞 이미지 + 16.67 ms)이 다음 합성과 겹친다. 그러면 60 fps로 바뀌는 화면(스크롤 등)에서 예열 프레임이 속도 조절 칸을 먼저 쓰고, 실제 이미지가 최대 12.5 ms 기다린다.
  - ±0.9 ms로 흔들리는 60 fps 소스의 단위 테스트 `TestWarmFeedLeavesAMovingScreenAlone`는 이 예외 없이 실패한다.
  - 실기기에서 움직이는 화면에 입력을 넣어 재지는 않았다.

1 ms 간격으로 보는 근거:
- 처음 구현은 다음 예열 시각까지 `AcquireNextFrame`(타임아웃 2 ms)으로 기다렸다. 그러자 하드웨어 예열이 37.6 fps(간격 p50 30.5 ms)에 그쳤다.
- `Encode` 호출은 1.1 ms였다. 그런데 AU가 나온 뒤 다음 `Encode`까지가 15.4 ms(p50)였다. 그 대기가 약 15.6 ms 단위로 끝났다.
- `NtQueryTimerResolution`은 1 ms였다. 그러나 Windows 10 2004부터 `timeBeginPeriod`를 부르지 않은 프로세스에는 기본 해상도보다 정밀한 대기가 보장되지 않는다([timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)).
- Go 런타임의 sleep은 고해상도 대기 타이머를 쓴다(`runtime/os_windows.go:399-406`, `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`).
- 그래서 창 동안 `Next(0)`과 1 ms sleep으로 바꿨고, 58.8 fps(간격 p50 17.0 ms)가 됐다.

### 9.2 클릭 지연

방법(`click`, `click1000`):
- 앞 입력에서 2.5초 쉰다. 그동안 예열 창이 끝나고 GPU가 쉬는 클록으로 돌아간다(첫 이동 때 GPU는 최종 실행 40번 중 33번 P8).
- 첫 번째 Same 버튼의 왼쪽(가운데에서 반폭의 0.7)부터 가운데까지 16 ms마다 포인터를 옮긴다. `click`은 320 ms 동안 21번, `click1000`은 1초 동안 63번이다.
- 앞 창과 `ui.at` 보호를 거친 뒤 클릭한다: down, 400 ms 뒤 up.
- 포인터는 버튼 위에서만 움직인다. 그래서 hover가 화면을 바꾸지 않는다(입력 전 프레임의 변화 최대 0픽셀).
- 첫 이동부터 클릭 down까지 p50은 354.5 ms와 1055.7 ms였다(보호 RPC 포함).
- `input`은 §4와 같다. 입력 간격이 1초 안팎이라 예열 창이 계속 열려 있다.
- 모두 각 20개이고, 보호를 모두 통과했으며 실패한 ACK는 없다.

### 9.3 GPU 클록

- 입력 없음(`static`, 60초): 표본 1,013개 중 P8이 953개다. P0 39개는 인코더를 만든 직후이고, P5 21개는 그 뒤 내려오는 동안이다. 예열은 일어나지 않는다.
- 예열이 계속될 때(`TestWarmFeedCPU`, 4K 정지 화면에 포인터 이동을 계속 주입):
  - P5에 머문다: 그래픽 1,035 MHz, 비디오 945–975 MHz. P0(비디오 1,305–1,470 MHz)까지는 오르지 않았다.
  - 그때 캡처→인코딩 완료는 13.5–13.9 ms다. P8에서는 약 28 ms였고, M6 진단의 P0에서는 8–9 ms였다.
- 오르는 속도: 쉬던 GPU에서 첫 이동부터 P8을 벗어나기까지 p50 360–416 ms(261–692 ms)가 걸렸다. 비디오 900 MHz 이상까지는 977–1,149 ms(858–1,461 ms)가 걸렸다(최종 `click` 17번, `click1000` 16번, 앞선 `click1000` 20번).
- 그래서 첫 이동 355 ms 뒤의 클릭은 20번 중 13번 P8에서 눌렸다. 1초 뒤의 클릭은 모두 P5 930 MHz 이상이었다.

- GUID `98332df8-03cd-476b-89fa-3f9e442dec9f`는 Windows SDK 10.0.26100 `um/codecapi.h:493`과 같다. 저장소의 다른 ICodecAPI GUID도 같은 헤더의 값과 같다(97, 106, 159, 232, 234, 344행).
- 예열 중에 다시 시험했다. 저장소에 넣지 않은 임시 빌드로 `TestWarmFeedCPU/hardware_warm`을 돌렸다(캡처→인코딩 완료 p50 / p95):

| 값 | p50 / p95 | 비트레이트 |
|---|---|---|
| 설정 안 함 | 13.56 / 14.06 ms | 2.73 Mbps |
| 0 | 13.51 / 14.30 ms | 2.77 Mbps |
| 100 | 16.06 / 16.45 ms | 2.71 Mbps |

- MFT는 이 속성을 받아들인다(100에서 2.5 ms 느려짐). 0은 기본값과 같으므로 설정하지 않았다.
- 이 세 실행에서는 GPU 클록을 함께 재지 않았다.

### 9.7 목표와 남은 시간

목표(클릭 → 변화한 프레임 수신 p50 ≤ 45 ms):
- 포인터를 1초 움직인 뒤 클릭하면(`click1000`) 40.4 ms로 닿았다.
- 입력이 계속될 때(`input`)는 46.9 ms로 닿지 않았다. 13.6(`SendInput`의 합성 대기) + 17.6(앱·합성) + 15.7(P5에서 인코딩 14 + 전송) ms다.
- 쉬던 GPU에서 355 ms만 움직인 뒤 클릭하면(`click`) 52.8 ms다. 9.3 + 18.0 + 25.5 ms이고, 클릭 때 GPU가 아직 P8이다.

남은 몫:
- 예열이 올리는 클록은 P5(비디오 약 945 MHz)까지다. P0에서는 인코딩이 5–6 ms 짧다. 60 fps 상한 안에서 그 이상 부하를 주는 방법은 없다.
- 쉬던 GPU가 P8을 벗어나는 데 약 0.4초, 945 MHz까지 약 1초가 걸린다.
- M6에서 D3D11 장치·H.264 MFT 생성 직후 약 2.2초 동안 P0가 되는 것을 봤다(§8.2). 쉰 뒤 첫 입력에 그런 생성을 일으키는 방법은 시험하지 않았다(드라이버 동작에 기대는 결정이 필요하다).
- `SendInput`의 합성 대기와 앱·합성 시간은 Windows와 앱의 몫이다(§8.3).
