## 2. 방법

- 시나리오(각각 새 QUIC 연결, `app.launch`로 fixture를 띄우고 `win.action focus`, 끝나면 `proc.kill`):
  - `static`: fixture(정지) 창이 앞에 있는 DISPLAY1, 60초. 화면 변화는 fixture의 Message 입력란 캐럿 깜빡임(스트림 시작 3.4초 뒤 멈췄다)과 작업 표시줄 시계뿐이다.
  - `motion`: `deskhand-fixture --animate`(640×360 논리 픽셀 = 960×540 물리 픽셀 패널을 합성마다 다시 그림), 60초, 원본 해상도.
  - `motion1920`: 같은 fixture, `max_width` 1920, 30초.
  - `input`: fixture(정지)에 클릭 20회, Space 20회(§4).
  - `keyframe`(M6): fixture(정지)를 띄우고, 새 `video` 스트림의 첫 AU 10회, 한 스트림에서 `keyframe` 요청 10회, 같은 설정의 `config`(인코더 재생성) 10회, `max_width` 1920과 원본을 오가는 `config`(출력 해상도 변경) 10회의 키프레임을 받고, 받은 직후마다 `screen.capture`(PNG, `max_width` 1920)를 찍는다(§8.1).
  - 모두 `video` 헤더 기본값(60 fps, 원본 4K는 20 Mbps, 1920은 6 Mbps).
- 시계 보정: 연결마다 측정 앞뒤로 `time.sync` 50회(5 ms 간격). 오프셋(에이전트 `mono_us` − 프로브 시계)은 RTT가 가장 작은 왕복의 `mono_us − (보낸 시각 + 받은 시각)/2`. 프로브 시계는 QPC.
- 캡처→수신 = 프로브 수신 시각 − (`capture_mono_us` − 오프셋). 첫 AU(인코더 생성 직후)는 따로 적고 분포에서 뺐다. 캡처→인코딩 완료는 `encode_done_mono_us − capture_mono_us`(에이전트 시계만 씀).
- 10초 반복 AU(protocol §4: 10초 동안 AU가 없어 마지막 이미지를 다시 인코딩한 AU)의 `capture_mono_us`는 이미지를 얻은 시각이 아니라 그 인코딩을 시작한 시각이다. M6부터 프로브는 앞 AU 캡처로부터 10.00–10.05초 뒤에 찍힌 키프레임 아닌 AU를 반복 AU로 보고 지연 분포에서 뺀다(n에 넣지 않는다). §3의 M5 `static` 행은 반복 AU 5개를 넣은 값이고, 같은 기록을 이 규칙으로 다시 계산하면 캡처→수신 10.24 / 100.12 ms(n 9), 캡처→인코딩 완료 9.94 / 92.43 ms다.
- 비트레이트·fps 평균은 스트림을 연 때부터 닫을 때까지의 AU 바이트·개수. 에이전트 `stats`(1초마다)도 함께 적었다.
- 디코딩: `ffmpeg -v error -i <x>.h264 -f null -`의 오류 줄 수, `ffprobe -count_frames`의 프레임 수.
- 백분위는 최근접 순위.

### 2.1 시계 보정의 불확실성

| 실행 | 최소 RTT | RTT 중앙값 | 빠른 8회 오프셋 폭 | 측정 뒤 오프셋 변화 |
|---|---|---|---|---|
| static | 0.168 ms | 0.198 ms | 0.021 ms | +0.001 ms |
| motion | 0.170 ms | 0.229 ms | 0.023 ms | −0.001 ms |
| motion1920 | 0.172 ms | 0.206 ms | 0.070 ms | −0.001 ms |
| input | 0.169 ms | 0.214 ms | 0.021 ms | −0.002 ms |

- 왕복 오차 한계는 최소 RTT의 절반, 약 ±0.09 ms.
- 에이전트의 `mono_us`는 Go 단조 시계이고, Windows에서 Go 1.26.0의 단조 시계는 `KUSER_SHARED_DATA`의 인터럽트 시각을 읽는다(`runtime/sys_windows_amd64.s:200`, `nanotime1`). 이 값은 타이머 틱마다(측정 중 1 ms) 바뀌므로, 같은 PC에서 Go 단조 시계의 증가 폭은 p50 1 ms(최소 0.44, 최대 1.69 ms, 1초 표본)였다. 그래서 에이전트가 찍는 `capture_mono_us`·`done_mono_us`는 실제보다 0–1 ms 이를 수 있고, 이 값을 쓰는 지연(캡처→수신, 주입 완료→변화 캡처)은 0–1 ms 크게 나올 수 있다. `time.sync`는 프로브가 5 ms 잠든 뒤(틱 직후) 보내므로 그 오차가 작고 빠른 8회의 오프셋 폭이 0.02–0.07 ms로 모였다.
- 결론(오차 = 측정값 − 참값):
  - 에이전트 시각이 끝점인 값(송신→주입 완료): −1.1 ~ +0.1 ms. 에이전트 시각이 이르면 값이 작게 나온다.
  - 에이전트 시각이 시작점인 값(캡처→수신, 인코딩 완료→수신): −0.1 ~ +1.1 ms.
  - 에이전트 시각끼리의 차(캡처→인코딩 완료, 주입 완료→변화 캡처): 두 시각이 각각 0–1 ms 이를 수 있어 −1 ~ +1 ms.
  - 프로브 시계만 쓴 값(ACK 왕복, 송신→변화 AU 수신)은 QPC라 이 오차가 없다.
  - 1 ms 틱보다 작은 차이(예: 클릭 up의 송신→주입 완료 0.29 ms와 Space up의 0.28 ms)는 잡음과 구별되지 않는다.

## 5. 발견

### 5.1 원본 해상도 첫 IDR이 검은 화면

8개 스트림 중 7개(4K 6개 전부, 1920 2개 중 1개)의 첫 AU(IDR)가 전부 검은 화면이다(4K 2,249 B, 1920 657 B; 디코딩한 첫 프레임의 밝기 최댓값 0). 다음 AU(P 프레임, 39–74 KB)가 4.9–76 ms 뒤 캡처한 화면 내용을 담고, 받는 쪽에서는 첫 AU 수신 뒤 5–18 ms 안에 도착했다. M6에서 원인을 확인하고 고쳤다(§8.1).

### 5.2 드문 프레임의 인코딩 지연

연속 움직임에서 캡처→인코딩 완료는 14.65 ms(4K)인데, 프레임이 드물 때(static, input)는 24–30 ms(p50)이다. 입력→화면 지연에서 가장 큰 몫이다. M6에서 원인(GPU가 쉬는 동안의 낮은 클록)을 확인했다(§8.2).

### 5.3 버튼 down 주입 시간

클릭 down의 ACK가 13.6 ms(p50)로 up(0.6 ms)이나 Space down(2.5 ms)보다 길다. 에이전트는 down과 up을 같은 경로로 처리하고 차이는 `SendInput` 호출 안에서 생긴다(송신→주입 완료 13.1 ms 대 0.3 ms). M6에서 잰 결과 그 시간은 저수준 훅 앞, Windows 입력 처리 안에서 다음 화면 합성까지 기다리는 시간이다(§8.3).

### 6.1 측정하지 않은 것

- **Mac↔PC 네트워크 구간.** PC 방화벽은 모든 프로필에서 켜져 있고 기본 인바운드 동작은 `NotConfigured`(Windows 기본값 차단)이며, Deskhand 허용 규칙은 설치된 에이전트의 UDP 47600뿐이다(다른 포트로 실제로 닿는지는 시험하지 않았다). 테스트 에이전트를 다른 포트로 띄우라는 결정과 보안 설정을 바꾸지 말라는 결정을 함께 지키려고, 방화벽 규칙을 더하지 않고 프로브를 PC에서 루프백으로 돌렸다. 그래서 위 지연에는 네트워크가 빠져 있다(인코딩 완료→수신 0.5–1 ms는 루프백 QUIC과 에이전트 쓰기 큐). 참고로 Mac→PC TCP 연결 왕복(포트 22, 40회)은 p50 4.68 / p95 15.10 ms(최대 69.3 ms)였다. 재측정: P1 병합 때 설치된 에이전트(47600)에 Mac의 `screen-probe run -addr <PC>:47600`으로 붙거나, 사람이 임시 방화벽 규칙을 허락하면 `run.sh`의 프로브를 Mac에서 돌린다.
- RDP 표시 상태(위 표).
- CPU 사용률(M3에서 4K60 움직임 논리 CPU 1개의 약 20.9%로 측정).

### 8.3 버튼 down의 `SendInput` 시간 — 원인은 Windows 입력 처리, 고치지 않음

- 에이전트 코드가 아니다: 에이전트는 `SendInput`을 한 번 부르고, 그 호출 자체가 13–16 ms 걸린다(진단 테스트에서 down p50 15.33 ms, 최소 11.10, 최대 16.44; up 0.37; 같은 점으로 이동 0.18).
- 다른 프로그램의 저수준 훅이 아니다: 테스트가 `WH_MOUSE_LL` 훅을 마지막으로(사슬의 맨 앞에) 걸었을 때 그 훅이 `SendInput` 시작 15.43 ms(p50) 뒤에야 불렸고, 그 안의 `CallNextHookEx`(나머지 훅 전부)는 0.004 ms(최대 0.152)였다. 훅이 이벤트를 삼키면(창에 닿지 않음) `SendInput`이 0.27 ms였다(삼키기 시작한 첫 번만 13.57 ms). 주입한 프로세스에는 시스템 밖 DLL이 없었고 `win32u!NtUserSendInput`의 앞부분은 손대지 않은 시스템 호출 코드(`4c 8b d1 b8 7a 10 00 00`)였다.
- 다음 화면 합성까지 기다린다: `DwmFlush` 직후 x ms에 down을 넣으면 `SendInput`이 16.7 − x ms 걸렸다(x = 0, 2, …, 14에서 16.72, 14.85, 12.97, 11.10, 8.99, 7.10, 5.08, 3.09 ms; x = 16에서는 다음 합성까지 17.62 ms).
- 대상에 따라 다르다: fixture의 `Same` 버튼(BUTTON) 위 down은 매번(쉬는 시간 0.2초·0.6초·3초, 이동과 한 묶음, 절대 좌표를 실은 down 모두 14.65–16.82 ms), Edit 위는 처음 두 번(15.06, 15.78 다음 0.50, 0.39), fixture 창 자체의 빈 곳은 창을 앞으로 가져온 뒤나 버튼을 누른 뒤 처음 한 번(8.71–16.97)만 기다렸고 그 뒤는 대부분 0.33–0.53 ms였다(처음 것을 뺀 50여 회 중 2회가 10.47, 13.04 ms). 빈 곳 down 앞에 3픽셀 이동이나 키 입력(그 창이 다시 그림)을 넣어도 대부분 0.35–0.48 ms였다.
- 결론: 기다림은 저수준 훅이 불리기 전, Windows 입력 처리 안에서 다음 DWM 합성까지다. Deskhand가 없앨 수 있는 시간이 아니고, 다른 프로그램이 원인이라는 증거도 없다. 그대로 두었다. 이 PC의 세션에는 입력을 지켜볼 수 있는 프로그램(Discord, Razer Central·Cortex, KakaoTalk, 1Password, `StSess.exe`·`nosstarter.npe`·`delfino.exe`·`I3GProc.exe`·`CrossEXService.exe` 등)이 떠 있으나 건드리지 않았다. Windows 안의 정확한 경로(커널 ETW 스택이 필요)와 다른 PC에서도 같은지는 확인 필요.
