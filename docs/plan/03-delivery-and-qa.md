# 03. 구현 순서·인수 테스트·완료 기준

## 1. 구현 순서

### M0 — 공식 Jump 경로와 세션 유지 검증

가장 먼저 Jump CLI Beta의 실제 버전과 MCP tool schema를 확보한다. 공식 배포/서명과 지원 조건을 확인한 후 별도 실험 환경에서 설치한다. 호스트 Connect 버전과 계정 플랜을 확인한다. 필요한 로그인은 준비된 화면에서 사용자에게 인계한다.

산출물:

- `capability-matrix.md`: 공식 문서 / 실제 제공 tool / 실측 pass·fail·blocked / 보완 주체.
- 동일 Windows 세션에 사람과 AI가 연결한 증거.
- Jump 뷰어가 열림·백그라운드·최소화·종료된 상태에서 각각의 화면/입력 결과.
- 공식 Mission Control takeover와 추가 helper/CDP 제어권을 함께 묶을 수 있는지에 대한 증거.
- 화면/UIA/명령/파일/디버깅/로그/QA별 부족한 부분, 재사용 가능한 부분.
- 채택 구조·언어·패키징·지원 버전·라이선스/비용을 기록한 ADR.

**판정:** 공식 Jump 경로가 목표를 충족하면 화면 전송/입력을 자체 개발하지 않는다. 충족하지 못하면 원인을 세션·화면·권한·네트워크로 분리하고 작은 대체 어댑터부터 검증한다. 제품 요구를 “사람이 항상 창을 띄워둠”으로 조용히 축소하지 않는다. 모든 로그인 사용자 화면이 사라진 경우까지 무조건 UI 동작을 보장하는 요구는 아니다.

### M1 — 공유 코어·연결·실행·파일

대상/세션 식별, 작업 저장·이벤트, 자동 재연결, 결과 불명확 처리, SSH/agent 어댑터, 파일 전송/이동을 만든다. CLI와 MCP는 동일 API를 사용한다. 명령·파일 작업의 중복 억제와 취소를 실제 장애 주입으로 검증한다.

### M2 — 화면·사람용 앱·제어권

공식 Jump 연동과 필요한 UI helper를 연결한다. 컴퓨터 목록, 작업 공간, 터미널, 파일 2패널, 전송 큐, 로그, 제어권 표시를 구현한다. AI 없이도 사람이 파일 전송·앱 실행·진단을 완료할 수 있어야 한다.

### M3 — 디버깅·QA·결과 수집

Electron main/renderer를 구분하고 최소 한 디버거에서 breakpoint→stack/variables→continue를 검증한다. 빌드 반입→실행→UI assertion→오류 수집→파일 반출을 하나의 QA 작업으로 묶는다. 실패를 재현하고 수정된 빌드로 재검증한다.

### M4 — 실사용 안정성·배포

클라이언트/원격 helper 충돌, 네트워크 단절, 재부팅, 잠금, 업데이트/롤백, 버전 불일치, 장시간 작업과 리소스 누수를 검증한다. 설치·MCP 등록·복구·제거 안내를 제공한다. 제품 기능과 현재 지원하지 않는 환경을 명시한다.

## 2. 필수 인수 테스트

각 테스트는 명령/앱 조작, 대상 버전, 시각, 기대값, 실제 결과, 증거를 남긴다. 아직 실행하지 않은 항목은 모두 `NOT_RUN`이다.

| ID | 대상 요구 | 테스트 | 통과 조건 |
|---|---|---|---|
| A01 | CON-01, REL-01 | 새 환경 설치와 등록 | 앱·CLI·MCP에서 같은 host와 capability 조회; 수동 터널 상시 관리 불필요 |
| A02 | CON-02 | Jump 사람 화면과 AI 화면 | 사용자/session/window 매핑 일치; 다른 세션에는 입력하지 않음 |
| A03 | CON-02, UI-01/02 | 뷰어 foreground/background/minimized/closed | 잠기지 않은 선택 세션에서 최신 캡처·입력·앱 assertion 성공; GUI 활성화 의존 없음 |
| A04 | CON-03 | 네트워크 30초 차단 후 복구 | 자동 reconnect, 기존 job 재부착; 파일·명령 중복 실행 없음 |
| A05 | CON-03, RUN-01 | 명령 실행 직후 응답 유실 | 완료/미실행/불명확 구분, request ID로 조회; 동일 명령 재실행 방지 |
| A06 | UI-03 | AI 입력 중 사람이 takeover | 모든 AI 입력 경로가 중단되고 사람 입력 가능; 이미 실행한 부작용은 정확히 표시 |
| A07 | UI-02/03 | 드래그/키 입력 중 취소·접속 종료 | 키·버튼이 눌린 상태로 남지 않음; 다른 앱에 뒤늦은 입력 없음 |
| A08 | UI-01/02 | 창 이동·DPI·다중 모니터 변경 | stale 좌표/요소 거절 또는 재관찰; 의도한 창만 조작 |
| A09 | UI-02 | 한글 IME·영문·줄바꿈·특수문자 입력 후 저장 | UI 화면과 저장 파일이 기대값에 일치 |
| A10 | CON-01, UI-03 | 잠금·로그아웃·UAC | UI는 정확한 대기/인계, 백그라운드 작업은 기능별 상태 유지; OS 보호 우회 없음 |
| A11 | RUN-01 | stdout/stderr·exit 7·timeout·PTY·stdin EOF | 출력/종료/취소 정확, 장기 실행 재부착 가능 |
| A12 | FILE-01/03 | 작은 텍스트·바이너리·1GiB·다수 파일 양방향 전송 | 바이트/hash 일치, 진행률·취소·재개; 초기 시험 크기이며 제품 크기 제한 아님 |
| A13 | FILE-02/04 | 이름 변경·이동·덮어쓰기 4정책 | 실제 경로/원본 상태 일치, 충돌 정책 준수 |
| A14 | FILE-03 | move 복사 실패·hash 불일치·원본 삭제 실패 | 검증 전 원본 삭제 없음; 부분 성공과 남은 원본 정확히 보고 |
| A15 | FILE-03/04 | 재개 중 원본 변경·디스크 부족·파일 잠금 | 오염된 최종 파일 없음, 재개/재시작 조건 설명 |
| A16 | FILE-01/02 | 한글·공백·이모지·긴 경로·case 충돌·junction | 경로 손상/탈출 없음; 지원하지 않는 조건은 명시적 오류 |
| A17 | DBG-01 | Electron main/renderer 연결·포트 충돌 | 대상 PID와 디버깅 역할 구분, 충돌 해결, 종료 시 자기 터널 정리 |
| A18 | DBG-02 | 실제 테스트 앱 breakpoint·stack·variables·continue | 정확한 소스/실행 위치와 변수 확인, 재개 후 앱 assertion 성공 |
| A19 | OPS-01, QA-01/02 | 의도한 앱 오류 재현·수정 빌드 재검증 | 첫 실행 실패 증거, 수정 후 동일 시나리오 pass, 실행 환경/버전 기록 |
| A20 | API-01 | GUI→CLI→MCP 교차 조회·취소 | 같은 job/transfer/event/artifact를 보고 제어 |
| A21 | REL-01 | host/helper/client 재시작·업데이트 실패 | 복구 또는 정확한 로그인 대기, 버전 불일치 감지, 롤백/증거 보존 |
| A22 | API-01, UI-03 | AI 2개와 사람 동시 접근 | UI writer 충돌 방지; 관찰과 실행 작업 소유권 표시 |
| A23 | QA-01/02 | 결과 export | 읽을 수 있는 HTML/Markdown와 기계 판독 JSON, 증거 manifest/hash |
| A24 | 전체 | 인증 실패·권한 부족·로그 점검 | 접근 거절, secret 노출 없음, 원인 있는 오류 |

RDP·VNC·Fluid 각각에 대해 A02/A03/A08/A10을 지원 조합별로 실행한다. 첫 출시의 기본 조합이 통과해도 다른 조합을 자동 통과 처리하지 않는다. 별도 ARM64/다른 OS는 별도 결과표로 관리한다.

## 3. 성능 측정 계획

기존 Windows-MCP 단발 실측은 전체 Snapshot 22~26초, 영역 Screenshot 0.43초였다. 이를 일반적 p95로 인용하지 않는다.

초기 제품 목표 제안: 정상 LAN/준비된 1080p 세션에서 screenshot p95 2초 이내, 대상 창 UIA 조회 p95 5초 이내, 단순 입력 ACK p95 1초 이내, 네트워크 복구 후 제어 채널 ready 15초 이내. 각 항목 최소 30회와 cold/warm 구분, OS/CPU/DPI/네트워크/프로세스 부하를 기록한다. 입력 후 앱 반응 시간은 ACK와 별도로 측정한다. 미달 시 원인과 근거를 남기고 목표 조정 또는 구현 개선을 결정한다.

전송은 같은 파일/네트워크의 기본 SFTP 또는 선택 transport를 기준으로 처리량, CPU, 메모리, 재개 손실량을 비교한다. 임의 속도 제한을 제품 기본값으로 넣지 않는다. 2시간 반복 관찰/입력/전송 후 작업·연결·프로세스·핸들 누수와 이벤트 저장 증가량을 확인한다. 더 긴 운영 시험은 P1로 확장한다.

## 4. 산출물과 종료 조건

구현 완료 보고에는 다음이 모두 있어야 한다.

- 설치 가능한 앱/CLI/원격 구성 요소, MCP 설정 방법과 실제 설치 환경 검증.
- 지원 capability/OS/아키텍처/프로토콜/버전 표와 제한.
- P0 인수 결과: PASS/FAIL/BLOCKED/NOT_RUN 구분. 핵심 P0가 남으면 전체 완료로 보고하지 않는다.
- 앱 실패 1개 이상의 실제 재현·원인 조사·수정 후 동일 테스트 통과 증거.
- Jump 뷰어 미표시 상태 및 연결 단절 후 복구 검증.
- 양방향 파일·폴더 전송, 이동 실패 시 원본 보존 검증.
- CLI·MCP만 사용한 실행과 사람용 앱만 사용한 실행 모두 통과.
- 작업 로그·스크린샷·덤프 등 결과물의 보존/삭제/비밀 제거 정책.
- 복구 runbook, 업데이트/롤백/제거 절차와 미완료 목록.

**금지되는 완료 판정:** 설치만 성공, MCP 도구 목록 조회만 성공, 메모장 입력만 성공, 모든 연결에 SSH 성공만 확인, API 200만 확인, 사람이 계속 수동 복구한 흐름을 자동 운용 성공으로 기록.
